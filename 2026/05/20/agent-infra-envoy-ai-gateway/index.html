Agent Infra - Envoy AI Gateway

Created2026-05-20|Agent InfraGateway
|Word Count:22.8k|Reading Time:96mins

Overview

Envoy AI Gateway is an open source project for using Envoy Gateway to handle request traffic from application clients to Generative AI services.

Usage

When using Envoy AI Gateway, we refer to a two-tier gateway pattern.

  1. The Tier One Gateway functions as a centralized entry point
    • handles authentication, top-level routing, and global rate limiting
  2. The Tier Two Gateway handles ingress traffic to a self-hosted model serving cluster
    • provides fine-grained control over self-hosted model access, with endpoint picker support for LLM inference optimization

Introduction

为什么需要专门的 AI 网关

背景：为什么要做这件事

  1. 当时行业有两股力量在博弈：
    • 商业网关（如 Kong Enterprise、AWS API Gateway）把 AI 流量管理功能锁在付费企业版里
    • 单公司开源（如 Portkey）虽然开源，但缺乏多公司协作的生态
  2. Tetrate（Envoy 商业公司）和 Bloomberg（大型金融企业用户）联手，选择在 CNCF Envoy 社区内做开放协作
    • 不是建新项目，而是在已有的 Envoy Gateway + Envoy Proxy 上扩展

核心论点：LLM 流量 ≠ 传统 API 流量

表面上看起来一样（客户端 → API 请求 → 后端服务），但本质不同

维度 传统 API LLM API
请求成本 固定（每次请求消耗差不多） 波动巨大（取决于 token 数量）
限流方式 按请求次数 必须按 token 数（计算复杂度的近似）
成本感知 QoS 为主 必须实时考虑成本
多后端 少量固定后端 多个 LLM Provider（OpenAI、AWS Bedrock 等），各自 API 不同

MVP 三大功能

Usage Limiting（Token 限流）

  1. 传统限流按”每秒请求数”不管用，因为一个长 prompt 的请求消耗远大于短请求
  2. 必须按 token 数（输入 + 输出）来控制用量和成本

Unified API（统一 API）

  1. 不同 LLM Provider 的 API 格式各异（OpenAI vs Bedrock vs Vertex）
  2. 网关对外暴露统一接口，客户端不需要关心后端是哪家
  3. 后续 v0.1 落地为 OpenAI 兼容 API

Upstream Authorization（上游鉴权）

  1. 多个 Provider 意味着多套 API Key 需要管理、轮换
  2. 网关集中管理凭证，客户端只需一个内部 token
  3. 后续演化为”凭证注入“模式

Reference Architecture

定义了 Envoy AI Gateway 在企业生产环境中应该怎么部署

核心架构：双层网关 (Two-Tier Gateway)

清晰的分层设计

为什么是两层而不是一层

分层的本质：关注点分离 - 外部访问的稳定性 vs 内部运维的灵活性，两层独立演进互不干扰

Tier 1 解决的问题

  1. 应用开发者面对多个 LLM Provider，API 格式各异 → 统一 API
  2. 每个 Provider 各自的 API Key 散落在各应用中 → 凭证注入，集中管理
  3. 无法全局控制和追踪用量 → 单点流量治理
  4. 安全策略不一致 → 集中策略执行

Tier 2 解决的问题

  1. 自托管模型有自己的运维节奏（版本升级、A/B 测试、扩缩容）
  2. 内部变更不应该影响外部客户端
  3. GPU 资源调度、模型缓存等是模型服务层面的关注点

KServe - 自托管模型服务

自托管是可选的 - 很多组织初期只用外部 Provider，后续按需引入 Tier 2

能力 意义
Token-based 自动扩缩容 按实际 LLM 负载弹性伸缩 GPU 资源
Scale-to-zero GPU 很贵，空闲时缩到零节省成本
多节点推理 (via vLLM) 大模型需要跨 GPU 分布式推理
OpenAI 兼容 API 与 Tier 1 网关的统一 API 对齐

生产就绪三大支柱

企业生产环境需要三个维度的能力

可观测性 (Observability)

  1. OTel 集成，遵循 GenAI Semantic Conventions
  2. OpenLLMetry 做细粒度 LLM 指标（prompt/completion 长度、token 吞吐）
  3. 集中式日志：跨 Provider 统一审计

控制 (Control)

  1. 用量防护栏：防止成本超支
  2. 合规执行：提示词安全检查、输出验证
  3. 不同于应用内嵌入检查，在网关层集中执行

优化 (Optimization)

  1. KServe 模型缓存降低推理延迟
  2. disaggregated serving - 将计算密集的推理阶段和内存密集的操作分开管理，最大化硬件效率

架构的可插拔性

  1. 可以只用外部 LLM，不要 Tier 2
  2. 可以用任何 Provider，不限于已支持的
  3. 可以加自定义 Envoy 扩展过滤器
  4. 可以跨集群、跨云部署 Gateway

Two-Tier Gateway Design

用两层网关解决企业 AI 平台的两个矛盾需求

为什么是两层，而不是一层？

先说问题：如果只用一层网关会怎样？单层方案的困境：

单层架构的本质问题是变更耦合

  1. ML 团队要发布新模型版本 → 需要修改网关配置 → 可能影响外部 LLM 流量
  2. 安全团队要调整认证策略 → 同时影响内部和外部流量
  3. 平台团队要调整 GPU 扩缩容 → 需要动生产网关

两层架构的本质是变更隔离

Tier 1 网关：外部访问的统一入口

职责边界

  1. 决定”这个请求应该去哪个 Provider“
  2. 不关心”那个 Provider 内部怎么路由”

为什么”开发者不需要知道后端是谁”很重要？

Tier 2 网关：内部模型的运维沙盒

具体场景

Tier 2 的变更 单层架构的影响 两层架构的影响
发布新模型版本 需要改生产网关配置，可能影响外部流量 只改 Tier 2，Tier 1 无感知
A/B 测试两个模型变体 配置混在一起，难以回滚 Tier 2 内部完成，Tier 1 看到的是同一个服务
GPU 扩缩容策略调整 可能影响网关稳定性 Tier 2 自治，Tier 1 继续服务
安全团队要加新的 Provider 鉴权 需要和 ML 团队协调模型路由变更 Tier 1 独立变更，Tier 2 不受影响

KServe 在 Tier 2 中的角色

三大特性：Routing and Traffic Management

Upstream Authentication with Credential Injection

问题场景：没有 Gateway 的凭证管理噩梦

  1. 12 个应用 × 5 个 Provider = 60 个 API Key 散落在各处
  2. Key 轮换需要改 12 个应用
  3. 开发者本地调试需要访问生产 Key

Gateway 的解决方案 - decouples applications from external secrets

  1. 应用代码不需要包含任何外部 API Key
  2. 开发者本地可以用内部 Token，环境隔离
  3. 安全审计只看 Gateway，不扫所有应用

Token-Based Rate Limiting and Cost Optimization

为什么请求次数限流不够？传统限流：每秒 100 个请求

Token 限流的实际作用 - Gateway 层面 - financial circuit breaker（金融熔断） - 保护钱包

  1. 策略：每分钟最多 10,000 tokens
  2. 请求 1-4 共 8007 tokens → 通过
  3. 再来一个 5000 token 的请求 → 被限流

estimated cost

  1. OpenAI GPT-4: 输入 $0.03/1K tokens, 输出 $0.06/1K tokens
  2. Gateway 可以在限流前先估算成本
    • 1000 tokens in + 500 tokens out ≈ $0.06
    • 策略：单请求不超过 $1，则通过
    • 策略：每天不超过 $100，则累计到 $100 后限流

Observability Hooks for Usage Patterns and Latency

没有统一 Gateway 时，多 Provider 的可观测性痛点

  1. OpenAI 的仪表板只能看 OpenAI 的用量
  2. Bedrock 的 Cost Explorer 只能看 Bedrock 的用量
  3. 没地方回答”团队 A 这个月在 LLM 上花了多少钱”
  4. 没法比较”同样用 GPT-4，哪个团队延迟最高”

Gateway 作为统一观测点 - Gateway OTel Metrics

  1. ai_gateway_request_tokens_total{provider=”openai”, model=”gpt-4”, team=”A”}
  2. ai_gateway_latency_seconds{provider=”anthropic”, model=”claude-3”}
  3. ai_gateway_cost_usd{team=”B”, provider=”bedrock”}

可以回答

  1. 哪个团队 token 用量最多？ → group by team
  2. 哪个模型延迟最高？ → group by model
  3. 新功能的 token 消耗如何？ → filter by feature tag

传统 HTTP 指标不够用

  1. request_count → 没法反映成本（前面说过的长短 prompt 问题）
  2. latency → LLM 的 TTFT（Time To First Token）更重要
  3. error_rate → LLM 可能”成功返回”但语义错误，需要专门的观测

GenAI 专用指标

  1. time_to_first_token_seconds（首字延迟） - TTFT
  2. prompt_tokens_total / completion_tokens_total（分开统计）
  3. streaming_chunks_total（流式响应的分块数）

总结：两层架构的权衡

层级 关注点 变更频率 影响范围 主要受益者
Tier 1 外部 Provider 接入、统一 API 低 所有外部客户端 业务开发者
Tier 2 自托管模型运维、版本管理 高 仅模型服务集群 平台/ML 团队

架构本质

  1. 用一个稳定的 Tier 1 吸收外部系统的复杂性
  2. 用一个灵活的 Tier 2 承载内部系统的快速迭代
  3. 两者通过统一的 API 解耦

KServe 与自托管模型服务

为什么需要 KServe？

问题：从训练到生产之间的鸿沟

一个模型科学家训练完模型后，要想变成一个可用的 API，需要以下步骤（但这些都不是 ML 领域的知识）

  1. 写 K8s YAML（Deployment、Service、Ingress…）
  2. 配置 GPU 资源请求和限制
  3. 实现健康检查和优雅关闭
  4. 搭建监控和日志
  5. 配置自动扩缩容策略
  6. 处理模型版本管理和灰度发布

KServe 的价值主张

KServe 的四大能力

Autoscaling（自动扩缩容）

传统 HPA（Horizontal Pod Autoscaler）的问题 - 传统 HPA 基于 CPU/内存指标

KServe 的 LLM 专属扩缩容 - Token-based autoscaling

Scale-to-zero for GPUs

Multi-node Inference via vLLM

大模型（如 Llama-3-70B）无法放入单个 GPU：

  1. A100 80GB → 放不下 Llama-3-70B
  2. 需要跨多个 GPU 分布式推理

vLLM 的多节点推理

KServe + vLLM 集成意味着：你不需要自己写分布式推理的代码，配置一下就能跑大模型

OpenAI-compatible APIs

为什么这个重要？客户端代码统一

这使 Tier 2 自托管模型能无缝接入 Tier 1 的统一 API - 客户端完全无感知

Model and Prompt Caching

Model Cache（模型缓存）

  1. 模型权重加载到 GPU 内存
  2. 多个请求共享同一份权重
  3. 不用每个请求都重新加载

Prompt Cache（提示词缓存）

  1. 很多请求有相同的 system prompt
  2. 缓存这些 token 的中间计算结果（KV cache）
  3. 避免重复计算，降低延迟

“Built-in support“ 意味着 KServe 已经处理好了这些优化，ML 工程师不需要自己实现

Backstage

Use tools like Backstage - Backstage 提供 UI/UX 层，让数据科学家不需要直接写 K8s YAML 或 kubectl 命令

Self-hosting is optional

两层架构不强制自托管，应该是渐进式采用路径

什么时候选择自托管？

因素 外部 Provider 自托管 + KServe
数据隐私 数据发到第三方 数据不出域
成本 按 token 付费 固定 GPU 成本（量大时更便宜）
定制 只能用官方模型 可以 fine-tune、自定义模型
运维 零运维 需要 K8s/GPU 运维能力
上线速度 立即可用 需要部署和调优时间

总结

KServe 在两层架构中的位置 - 让 ML 工程师不需要成为 K8s 专家，就能把模型部署成生产级服务

Control（控制）

在 Gateway 层集中执行策略，而不是散落在每个应用里 - 策略分散在应用（反模式） - 策略不一致、维护成本高、容易遗漏

策略集中在 Gateway（推荐） - 只需要做业务逻辑，策略由 Gateway 保证

Prompt Misuse（提示词滥用）

  1. 用户试图通过越狱绕过安全限制
  2. 恶意用户注入有害内容
  3. 解法：Gateway 层可以做输入过滤

Model Hallucination（模型幻觉）

  1. 模型输出虚假或错误信息
  2. 解法：Gateway 层可以做输出验证（如事实核查）

Control quality and compliance centrally

  1. 安全策略变更只需要改 Gateway，不需要改所有应用
  2. 合规审计只看 Gateway 日志，不需要扫所有应用
  3. 新应用默认继承所有策略，不需要重复实现

具体问题拆解

KV-Cache 的影响

  1. 相同请求 “继续刚才的话题”
    • 节点 A（有 KV-Cache）: 100ms
    • 节点 B（无 Cache）: 2000ms
  2. 传统 LB: 看不出区别，可能路由到节点 B
  3. EPP: 知道节点 A 更快，自动路由到 A

队列深度 (Queue Depth)

  1. 区别
    • 节点 A: 1 个请求在处理，但 GPU 空闲（等待 I/O）
    • 节点 B: 1 个请求在处理，GPU 满载
  2. 传统 LB: 看队列长度都是 1，随机选
  3. EPP: 知道节点 A 实际更空闲

LoRA 适配器

  1. 请求需要 LoRA-X 模型
    • 节点 A: 已加载 LoRA-X → 直接用
    • 节点 B: 需要重新加载 LoRA-X → 等待 5 秒
  2. 传统 LB: 不知道模型状态，可能路由到 B
  3. EPP: 知道节点 A 有适配器，优先路由

现实后果对比

场景 传统负载均衡 EPP 智能路由
负载不均 热点过载 + 其他节点空闲 均衡利用 GPU
延迟 P99 延迟高（命中差节点） P99 延迟优化
成本 需要过度配置 资源利用率高
运维 手动调整权重/下线节点 自动适应

结论

  1. AI 推理的状态性（KV-Cache、模型加载、队列状态）使得传统无状态负载均衡失效
  2. 需要像 EPP 这样理解 AI 特定语义 的路由机制
